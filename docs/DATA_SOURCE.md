# DATA_SOURCE — MLB 資料來源

本文件的內容來自官方與社群文件、社群程式碼的搜尋結果，**沒有實際打過 API 驗證**，除非標註為已驗證。2026-10-03 的 M0 探針已驗證大部分端點與欄位，結果見 `PROBE_REPORT.md`；本文件的【未驗證】標記以該報告為準。標記說明見 `CLAUDE.md`。第一個任務就是用探針腳本把「【未驗證】」變成「已驗證」或「與文件不符」。

## 1. 基本事實

- 基底網址：`https://statsapi.mlb.com/api/v1/`。社群與多個第三方說明大部分端點不需要 API key、註冊或驗證。
- 官方文件在 docs.statsapi.mlb.com，有資料說明其存取透過 MLB 的身分提供者對合作夥伴把關。也就是說，公開端點「能用」較接近被容忍的現狀，並非正式承諾。【未驗證】
- 沒有穩定的官方公開規格，端點與欄位隨時可能改變。程式碼要容忍欄位缺失。
- 社群整理的端點清單：toddrob99/MLB-StatsAPI 的 wiki。

## 2. 端點（除 `/schedule/postseason` 系列外，2026-10-03 已驗證可用，見 `PROBE_REPORT.md`）

| 用途 | 端點 |
| --- | --- |
| 逐場即時資料（GUMBO） | `GET /api/v1.1/game/{gamePk}/feed/live` |
| 只取差異 | `GET /api/v1.1/game/{gamePk}/feed/live/diffPatch`（參數：`startTimecode`、`endTimecode`） |
| 列出一場比賽所有時間碼 | `GET /api/v1.1/game/{gamePk}/feed/live/timestamps` |
| 取指定時間點的狀態 | `feed/live` 帶 `timecode` 參數 |
| 局分表 | `GET /api/v1/game/{gamePk}/linescore` |
| 賽程與全聯盟比分 | `GET /api/v1/schedule`（參數：`sportId`、`date` 或 `startDate`/`endDate`、`gameTypes`、`hydrate`） |
| 季後賽賽程 | `GET /api/v1/schedule/postseason`、`/schedule/postseason/series` |
| 賽事類型代碼 | `GET /api/v1/gameTypes` |
| 球隊清單 | `GET /api/v1/teams?sportId=1` |
| 球員本季成績（季後賽時球員卡的例行賽數字） | `GET /api/v1/people?personIds=…&hydrate=stats(group=[hitting,pitching],type=[season],season=…,gameType=R)&fields=…`（2026-10-04 已驗證：換過隊的球員有各隊一筆加合計一筆，合計那筆排第一、只有它帶 `numTeams`；`fields` 篩選後一場 52 人從 133,061 位元組降到 12,623） |

備註：
- 一場九局比賽結束後，`feed/live` 的回應可達四萬行 JSON，包含每個 play 與每顆球。輪詢整包會隨比賽進行越來越大，所以要評估 `diffPatch`。
- 回應內的 `currentPlay` 區段只包含當前打席。
- 賽程端點會回傳所有賽事類型（春訓、例行賽、季後賽、明星賽、表演賽）。社群提到單次日期範圍有上限（約 62 天）。
- 每場比賽的 `gamePk` 從賽程取得。

## 3. 可能有用的欄位【未驗證，以實際 payload 為準】

- 比賽狀態：局數、上下半局、出局、球數、壘上跑者、比分、比賽狀態碼。
- 投球：球種、球速、經過本壘板的位置（plate 座標）、好壞球判定。
- 擊球：擊球座標、仰角、初速、距離、結果事件類型。
- 防守站位或 shift 資訊（是否存在待確認）。
- 2026 年起好球帶上下緣改用 ABS 自動好球帶定義，相關欄位的語意以實際資料為準。

## 4. 季後賽

- 賽程端點本來就包含季後賽；可用 `gameTypes` 篩選，或使用 `/schedule/postseason`。
- 社群參考文件列出的代碼：F（外卡）、D（分區系列賽）、L（聯盟冠軍賽）、W（世界大賽）、P（全部季後賽）。其中 F 被描述為舊制的外卡單場，現行是外卡系列賽。**已驗證：2026 外卡系列賽的實際代碼是 `F`，分區系列賽是 `D`。**
- 2026 季後賽時程（已查證）：外卡系列賽 9/29 至 10/1；分區系列賽 10/3 起；聯盟冠軍賽 10/11 起；世界大賽 10/23 起，最晚 10/31。

## 5. 已結束比賽與回放

- 已結束比賽用同一個 `gamePk` 打 `feed/live` 即可取得完整資料，已有開源專案用已結束比賽的資料重播並驅動 3D 動畫。
- 搭配 `timestamps` 取得時間碼，再用 `timecode` 逐步取得各時間點狀態，即可重播。
- 邊界【未驗證】：多早以前的比賽仍有完整的逐球資料。M0 要實測數個賽季並記錄。

## 6. 資料的限制（影響設計）

- 公開資料是**事件式**的，不是連續的球員追蹤。野手與跑者的動作要在已知狀態之間做風格化補間。
- 公開資料比電視轉播慢，且無法取得付費層級的低延遲。本專案不提供也不宣稱與轉播同步。
- 輪詢節奏、實際延遲、欄位完整性都要在 M0 與 M2 量測並記錄。
- 2026 年起因 ABS 挑戰制，MLB Gameday 的投球落點資料延遲 5 秒釋出，轉播畫面的好球帶框延遲約 9 秒（<https://awfulannouncing.com/mlb/abs-broadcast-nine-second-delay-gameday-strike-zone.html>）。Stats API 的 `pX`／`pZ` 是否同樣延遲【未驗證】，直播量測時一併確認。對陪伴用途影響不大。

- 聲明內容大意：資料與其呈現是 MLBAM 的專有內容；只允許個人、非商業、非大量的使用；其他用途須事先取得 MLBAM 的書面授權；被授權者也不得做超出授權的商業用途。
- MLB 的網站使用條款另規定：除個人非商業的家庭使用外，未經書面許可不得重製、衍生、散布或公開展示其數位資產。
- 「大量」沒有被定義。

### 7.2 本專案的做法【建議，與使用者討論的結論一致】

1. 只在使用者本機直接抓取。**不經任何自建伺服器轉發**，不託管，不提供服務。
2. 不商業化。不收費、不放廣告、不接贊助置入、不做付費功能。【已決定 2026-10-03】唯一例外是自願捐款，用 Buy Me a Coffee，**只放在 repo**：README 的 Support 段與 repo 頁的贊助按鈕（`.github/FUNDING.yml`）。【已決定 2026-10-04】App 裡不放贊助連結（原本在「關於」頁）：有些看板把贊助連結當成營利，App 本身保持完全沒有金流的樣子。App 的對外連結只有專案網站（basesmall.chroniclecore.com）與原始碼；網站頁尾有贊助與工作室連結，寫明贊助不會解鎖任何功能。
3. 節流輪詢，避免對 MLB 伺服器造成負擔；不做批次或大量抓取。
4. 不重新散布 MLB 的資料集。夾具只供測試使用，倉庫中的夾具需評估是否適合公開提交，**預設不提交完整的 MLB 回應檔**。【待決】
5. README 要附：資料來源說明、MLB 版權聲明的連結、與 MLB 無隸屬關係的聲明。
6. 不使用球隊 logo、字樣、背號、官方商標或整套球衣的重現作為美術或行銷素材。球隊以文字名稱或縮寫表示。【2026-10-03 放寬】隊色與簡單圖樣（細條紋）可以用：它們不是商標本身，本專案也不使用任何 logo。
7. 開源授權只涵蓋本專案程式碼，不涵蓋資料。要在 README 寫清楚。
8. 這些不構成法律意見。正式發布前，使用者應自行閱讀條款原文。

## 8. 探針腳本（第一個任務）

請寫一個小腳本（語言不限，建議 Node 或 Python），做以下事情並輸出報告：

1. 取得某一天的賽程，確認 `gamePk`、狀態與賽事類型欄位，並確認季後賽賽事類型的實際代碼。
2. 對一場已結束的比賽取 `feed/live`，列出：
   - 投球資料中實際存在的欄位。
   - 擊球資料中實際存在的欄位（座標、仰角、初速、距離）。
   - 是否有防守站位資訊。
3. 取 `timestamps` 並以兩個不同的 `timecode` 取狀態，確認回放可行。
4. 對一場進行中的比賽（若當下有），測量：回應大小、輪詢延遲、以及與電視轉播相比的落差（無法比較就記錄為未知）。
5. 對 `diffPatch` 做同樣的測試，比較回應大小。
6. 另外確認：webview 直接 `fetch` 是否遇到 CORS。
7. 數個賽季的已結束比賽抽樣，記錄最早仍有完整逐球資料的賽季。
8. `/teams` 回應是否含球隊代表色欄位（棋子配色用，見 `ARCHITECTURE.md` 4.8）。
9. 為了產生中英文事件文字：每個 play 除了英文描述句之外，是否有結構化的事件類型、擊球方向或守備位置、打點、跑者移動（見 `ARCHITECTURE.md` 4.9）。
10. 原型「投打對決」視窗需要的欄位：投手當場用球數、局數、三振；打者當日成績。預期在 boxscore 區段。
11. 賽程端點能否用 `hydrate` 一次帶出各場 linescore（全聯盟通知用）。
12. 把結果寫成 `docs/PROBE_REPORT.md`，並依實際結果更新本文件與 `docs/ARCHITECTURE.md` 的資料模型。

過程中請遵守 7.2 的做法：低頻率、單一進行中請求、不做大量抓取。
